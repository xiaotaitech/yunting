## Context

目标是做一个「帆书体验 + 百度网盘数据源」的听书 App。与帆书最本质的区别是：帆书拥有内容库，我们没有——我们只是用户自己网盘的一个更好的播放前端。这一条决定了几乎所有架构选择：不托管音频、不建内容数据库、不做内容分发。

### 百度网盘开放平台的既有约束（调研结论）

这些是外部给定的、不可协商的前提，设计必须绕着它们走：

| 约束 | 影响 |
|---|---|
| OAuth 2.0 授权，`scope` 必须固定传 `basic,netdisk`，传错调接口返回 `errno=-6` | 授权层写死 scope，不做可配置 |
| 下载是三段式：`列表接口拿 fs_id` → `filemetas?dlink=1 拿 dlink` → `dlink + &access_token=xxx 下载` | 播放一个章节至少 1 次额外 API 往返，需要缓存 dlink |
| dlink 的 **Range 请求**必须带 `User-Agent: pan.baidu.com`（与文件大小无关，见下方实测修正） | 流播/seek/断点续传全靠 Range，所以这仍是硬约束；也是排除浏览器方案的理由之一 |
| dlink 会 302 跳转到真实 CDN 地址，且有时效性（小时级） | 播放器必须能处理重定向 + 链接过期后无感重取 |
| dlink 支持 HTTP `Range`，可断点续传 | 流式播放（seek）与断点下载在协议层是可行的 |
| 分享类接口不对个人开发者开放 | 「分享书单/分享链接导入」这条路走不通，不列入路线图 |
| 非会员账号下载带宽受限 | 高码率音频可能无法稳定流播，必须有下载兜底与缓冲策略 |
| 有 server 的应用必须在控制台配置授权回调地址 | OAuth 代理需要固定域名，不能用临时地址 |

### 修正：UA 约束的真实形态（2026-08-30 实测）

上表第一条原本抄自 AList 文档与旧博客：「不带 `pan.baidu.com` 的 UA，>20MB 会被拒」。
拿真实账号逐项对比后，**这个说法是错的，但底下确实有一条约束，只是形态不同**：

| 请求 | UA | 结果 |
|---|---|---|
| 完整 GET（50.2 MB） | `pan.baidu.com` | HTTP 200 |
| 完整 GET（50.2 MB） | `Mozilla/5.0` | **HTTP 200 —— 并未被拒** |
| Range `bytes=0-65535` | `pan.baidu.com` | HTTP 206 |
| **Range `bytes=0-65535`** | **`Mozilla/5.0`** | **HTTP 403** |

**真相：UA 校验只发生在 Range 请求上，与文件大小无关。**

这对本项目意义重大——流式播放、seek、断点续传、读 ID3 头，**全都靠 Range**。
所以 UA 对我们仍然是硬性要求，只是原因跟传闻说的不是一回事。

顺带，它也重新支撑了排除 Web 的结论：浏览器的 `<audio>` 播放长音频必然发 Range，
而浏览器不允许改 UA → 必然 403。加上 `d.pcs.baidu.com` 不发 CORS 头、
`sqflite` 在 Web 不可用，**Web/PWA 三重堵死**。

### 由此引出的实现级陷阱：dart:io 重定向会丢 UA

修正上面那条的同时，实测又暴露了一个只在真实链路上才会出现的问题：

| 客户端写法 | 结果 |
|---|---|
| `followRedirects=true`，只在请求 header 里设 UA | **HTTP 403** |
| `followRedirects=true` + 同时设 `HttpClient.userAgent` | HTTP 206 |
| 手动跟随重定向，每一跳都重设 UA | HTTP 206 |

**dlink 会 302 跳到 CDN，而 dart:io 跟随重定向时会丢掉请求 header 里的 User-Agent**，
换回它自己的默认值 `Dart/x.y (dart:io)`。

症状极具迷惑性：完整 GET 一切正常（无 Range 时百度不查 UA），
只有读 ID3、seek、断点续传这些用 Range 的地方全线 403，而且报出来是
「播放地址已失效」——看着像 dlink 过期，其实跟过期毫无关系。

修法：UA 必须**同时**设在 `HttpClient` 上，才会跟着重定向一起走。

教训有两条：把二手资料当硬约束写进设计，要尽早用真账号证伪；
而证伪之后也别急着走到另一个极端——「UA 不必要」同样是错的，
正确答案在更细的粒度上（只对 Range 生效）。

### 前置阻塞项

百度网盘开放平台需要开发者注册 + 实名认证 + 应用创建审核。这是**外部依赖，不在本变更的代码工作量内，但会阻塞联调**，须最先启动。

## Goals / Non-Goals

**Goals:**
- 用户授权自己的百度网盘后，能把网盘里的音频文件夹当成「书」来听，体验对齐主流听书 App。
- 播放链路对网盘的不稳定（限速、dlink 过期、302）具备韧性，用户感知不到底层是网盘。
- 服务端组件保持在「一个 OAuth 函数」的规模，零数据库、零内容托管、零运维负担。
- 进度与书架跨设备同步，但同步载体是用户自己的网盘，不是我们的服务器。

**Non-Goals:**
- 不做内容库、不做版权采购、不做听书稿/AI 摘要（这是帆书的商业模式，不是本项目的）。
- 不访问用户网盘之外的任何数据源：不抓分享链接、不爬第三方资源站、不做「资源搜索」。
- 不做社区、评论、打卡、训练营。
- MVP 不支持 Web 端（UA 约束使其不可行，见 D1）。
- 不做多网盘（阿里云盘 / 夸克 / OneDrive）——但数据源接口留抽象，见 D9。

## Decisions

### D1：客户端用 Flutter，放弃 Web/PWA

**决定**：Flutter 单代码库出 Android + iOS，音频层用 `just_audio` + `audio_service`。

**理由**：
- `just_audio` 的 `AudioPlayer(userAgent: 'pan.baidu.com')` 以及 `setUrl(url, headers: {...})` 能直接满足百度对 UA 的强制要求；它在 Android 侧走 ExoPlayer、iOS 侧走 AVPlayer（iOS 16+ 用 `AVURLAssetHTTPUserAgentKey`，更低版本走本地代理），且已修过「重定向时 UA 丢失」的 bug——正好命中我们的 302 场景。
- `audio_service` 提供后台播放、通知栏/锁屏控制、耳机线控，这是听书 App 的及格线。

**否决的替代方案**：
- *Web / PWA*：三重堵死。① 浏览器播放长音频必然发 **Range**，而百度对 Range 校验 UA，
  浏览器又不允许改 UA → 必然 403；② **CORS**：`d.pcs.baidu.com` 不发跨域响应头；
  ③ `sqflite` 在 Web 上不可用。唯一出路是自建代理中转全部音频流量——那等于我们成了
  内容分发方，成本与合规风险都最高。**直接排除。**
- *Android 原生 (Media3)*：能力最强、缓存控制最细（`CacheDataSource` 开箱即用），但只出安卓，后续补 iOS 等于重写。
- *iOS 原生*：AVPlayer 改 UA 在 iOS 16 以下要靠本地 HTTP 代理绕，反而更绕。

**代价**：Flutter 的离线缓存不如 Media3 的 `CacheDataSource` 现成，需要自己实现下载+本地文件切换（见 D6）。

### D2：服务端只保留一个 OAuth 代理，其余全客户端直连

**决定**：唯一的服务端是一个 serverless 函数，暴露两个端点：`POST /oauth/exchange`（code → token）和 `POST /oauth/refresh`（refresh_token → 新 token）。SecretKey 只存在于该函数的环境变量里。所有网盘文件接口（列表、filemetas、dlink 下载）由客户端**直连百度**，流量不经过我们。

**理由**：
- SecretKey 绝不能进客户端二进制（可被反编译提取）。
- 但一旦让服务端代理文件流量，我们就承担了带宽成本 + 内容中转的合规风险。所以边界划在「只代理凭证，不代理数据」。

**否决的替代方案**：
- *完全零后端（implicit 授权）*：只能拿到短期 access_token、拿不到 refresh_token，用户每隔一段时间就要重新授权，体验不可接受；且 AppKey 暴露。
- *完整后端*：自建用户体系 + 元数据库 + 刮削服务。功能上更强（可以做全局书籍元数据库），但要服务器、要备案，且一旦缓存音频就变成内容托管方。规模不匹配。

### D3：dlink 生命周期管理——「懒取 + 缓存 + 过期无感续播」

**决定**：引入一个 `PlaybackUrlResolver`，是章节 URL 的唯一来源：

1. 章节仅持久化 `fs_id` 和 `path`，**绝不持久化 dlink**（它会过期，存了就是脏数据）。
2. 播放/下载前调 `filemetas?dlink=1` 换 dlink，在内存中缓存，TTL 取保守值（远小于百度的实际有效期），并按 `fs_id` 键控。
3. 播放中若底层报 403/410/连接中断，`PlaybackUrlResolver` 强制作废缓存、重取 dlink，播放器用新 URL 重新 `setUrl` 并 `seek` 回中断位置——**用户只感知到一次短暂缓冲**。
4. 重试用指数退避，连续失败 N 次才向用户报错，并区分「token 失效」（跳授权）与「网络/限速」（可重试）两类。

**理由**：dlink 过期是这个 App 最高频的故障源。把它收敛到单一组件、并在播放层做位置保持的自动恢复，是把网盘的不可靠性挡在用户体验之外的关键。

### D4：书目模型——「文件夹即书」，用户主动认领，不全盘扫描

**决定**：用户从网盘目录树里挑一个文件夹，点「加入书架」，该文件夹即成为一本书；其中的音频文件按自然序成为章节。支持一层子目录（卷/季）。

**理由**：
- 全盘扫描要遍历用户整个网盘、拉海量 `filemetas`，慢、费配额、且误判率高（网盘里什么都有）。
- 认领制让用户对「哪些是书」有完全控制权，也天然避免了扫到隐私文件。

**章节排序**：按文件名做自然排序（`第2章` 排在 `第10章` 之前，`ch2.mp3` 排在 `ch10.mp3` 之前），从文件名中抽取数字段做数值比较而非字典序比较。若文件 ID3 tag 里有 `track` 号则优先采信 tag。排序结果对用户可见且可手动调整。

**元数据来源**（按优先级）：① 用户手动编辑 → ② 音频 ID3 tag（标题/专辑/作者/内嵌封面）→ ③ 同目录下的封面图文件（`cover.jpg`/`folder.jpg` 等）→ ④ 文件夹名兜底。**MVP 不做联网刮削**（豆瓣/第三方 API），避免引入不稳定的外部依赖。

### D5：状态同步——写回用户自己网盘的 `/apps/` 目录

**决定**：书架、每本书的播放进度、收藏，序列化为一个 JSON，存到用户网盘的 `/apps/<应用名>/library.json`。本地用 SQLite/Isar 做权威读写与离线可用，后台按节流策略上传合并。

**冲突解决**：每条记录带 `updatedAt`（客户端时钟）与 `deviceId`，合并时**按记录粒度取 last-write-wins**，而不是整文件覆盖——这样「手机上听到第 5 章、平板上加了一本新书」不会互相抹掉。

**理由**：零服务端数据库、零用户体系，数据主权完全在用户手里（卸载 App 数据还在，换手机自动恢复）。`/apps/` 是网盘给应用的专属目录，不污染用户文件区。

**代价**：LWW 在设备时钟严重偏移时会误判；节流上传意味着跨设备同步是最终一致而非实时。对听书场景可以接受。

### D6：限速与缓冲——流播为主，下载为兜底

**决定**：
- 默认流式播放，播放器设置较大的预缓冲窗口（听书是线性顺序消费，不像视频要频繁 seek，可以激进预缓冲）。
- 播放当前章节时，**后台静默预取下一章**的 dlink 与前若干秒数据，减少章节切换的静默间隙。
- 若实测下行速率持续低于码率所需，UI 明确提示「网络较慢，建议先下载」，并提供一键下载本书。
- 离线下载走独立的下载队列（并发受限，支持 `Range` 断点续传），不与播放争带宽。

**理由**：非会员网盘限速是已知的、我们无法解决的外部条件。设计上不假装它不存在，而是让用户可以用「提前下载」换取确定性的体验。

### D7：离线缓存的存储与配额

**决定**：下载文件按 `<书 id>/<章节 fs_id>.<ext>` 落在 App 私有目录（不进系统媒体库，避免被其他 App 扫到）。维护一个缓存索引表，支持按书查看占用、单本删除、全局配额上限 + LRU 自动清理。播放时 `PlaybackUrlResolver` **优先返回本地文件路径**，本地不存在才去取 dlink。

**理由**：本地优先让离线播放和「已下载的书不再消耗流量」自然成立，且这个判断点和 dlink 解析收敛在同一个组件里，没有第二处分支。

### D8：合规边界写进架构，而不只是写进文案

**决定**：
- 客户端只调用「读取当前授权用户自己的文件」相关接口。**代码里不存在**任何调用分享类接口、解析分享链接、或访问非本人网盘的路径。
- 服务端不落任何用户文件元数据，不落音频，日志不记录文件名/路径。
- App 内不提供搜索他人资源、导入分享链接的入口。

**理由**：这类工具最大的风险不是技术，是被认定为盗版资源分发渠道。把「做不到」做成架构事实（而非产品承诺），是最有效的自我保护。

### D9：数据源接口留抽象，但 MVP 只实现百度

**决定**：定义 `CloudDriveSource` 接口（列目录、取文件元数据、解析可播放 URL、下载），百度网盘是它的第一个实现。UI 与播放层只依赖接口。

**理由**：抽象成本很低（就是一个接口），但把未来接阿里云盘/夸克/WebDAV 的可能性留住了。**MVP 不实现第二个 driver**，避免为假想需求过度设计。

## Risks / Trade-offs

- **百度开放平台应用审核不通过或个人开发者权限受限** → 这是项目级的单点风险。缓解：**在写第一行客户端代码之前**先完成注册、实名、建应用，并用最小脚本跑通「授权 → 列目录 → 取 dlink → 带 UA 下载一个大音频文件」的完整链路（见 tasks.md 的 Phase 0）。链路跑不通，整个项目的前提就不成立。
- **非会员限速导致高码率音频无法流播** → 缓解：预缓冲 + 下一章预取 + 明确的「先下载」引导（D6）。有声书常见码率（64–128kbps）压力不大，但无损/高码率资源需要下载兜底。
- **dlink 过期造成播放中断** → 缓解：`PlaybackUrlResolver` 的自动重取 + 位置保持续播（D3）。这是必须做对的一条，要有专门的测试用例（人为作废链接后验证续播）。
- **百度接口/策略变更（UA 要求、限速规则、接口下线）** → 缓解：网盘访问全部收敛在 `CloudDriveSource` 的百度实现里，变更影响面可控；D9 的抽象也是这个风险的对冲。
- **LWW 同步在时钟偏移下丢更新** → 缓解：记录粒度合并而非整文件覆盖；进度类字段额外用「取更大的播放位置」而非纯时间戳，减少「回退到旧进度」这种用户最反感的表现。
- **iOS 后台音频与审核** → 需正确声明后台音频能力。App Store 审核对「网盘播放器」类应用可能追问内容来源，需准备好「仅访问用户自有存储」的说明。
- **Flutter 离线缓存需自研** → 相比 Media3 `CacheDataSource` 是明确的额外工作量，已在 D7 中界定为独立模块，不与播放器耦合。
