## Context

书架页（`ui/shelf_screen.dart`）现在是一列同构卡片，每张卡片右侧带一个「继续收听」按钮（`_continueListening`：取章节 → `handler.openBook(book, chapters)` → `play()` → push 播放页）。能力已经齐了，缺的只是把最近在听的那本从列表里拎出来放到首屏。

手上现成的材料：

- `BookDao.allBooks()` 已按 `COALESCE(last_played_at, added_at) DESC` 排序，`shelfProvider` 直接暴露它。但排头的书不一定播放过——从未播放的书会用 `added_at` 参与排序，所以「最近在听」必须显式筛 `last_played_at != null`，不能拿 `shelf().first` 当答案。
- `Book` 已带 `currentChapterIndex` / `currentPositionMs` / `finished` / `sourceMissing`，且这三者随 `library.json` 跨设备同步（`library_snapshot.dart`）。
- `AudiobookHandler.openBook(book, chapters)` 在不传 `chapterIndex` 时就用书上的断点，并已实现「听完的书重播从头」。
- 章节标题要另取：`Book` 上只有序号，`library.chapters(bookId)` 才有标题。

约束：首屏渲染 MUST NOT 依赖网络。冷启动时 token 可能在刷新、网盘可能不可达，卡片要在本地库读完的一瞬间就能显示。

## Goals / Non-Goals

**Goals:**
- 冷启动首屏第一眼就是「上次听到哪」，一击续播。
- 卡片与列表上既有的「继续收听」共用同一条续播路径，行为不会分叉。
- 换设备后仍然正确——依据跨设备同步的书目进度，而非本机历史。
- 所有异常态（书源丢失、章节未解析、已听完）在卡片上先讲清楚，而不是点下去才暴露。

**Non-Goals:**
- 冷启动自动播放（明确不做，见下）。
- 首页「最近在听」横向多本列表。
- 改动播放层、本地库结构或同步文件格式。

## Decisions

### 决策 1：数据源用 `books` 表，不用 `play_history`

`play_history` 里有现成的「最近一条」，`HistoryDao.recent(limit: 1)` 一句就能拿到书名、章节名、断点，看起来更省事。但历史按规格只存本机、不进同步文件——换台设备打开，历史是空的，而书架与进度是在的。首页续听要是空着，用户会以为进度丢了。

所以取 `books` 中 `last_played_at` 最大且非空的一本，章节标题用 `library.chapters(bookId)[currentChapterIndex]` 现取。代价是多一次章节查询（本地 SQLite，可忽略），换来的是「换设备也接得上」。

**备选方案**：两者取较新的一个。否决——两套数据在同一台设备上本就同源，合并只会引入「显示的书和播的书不一致」这类难查的偏差。

### 决策 2：新增 `continueListeningProvider`，返回一个组合值

```
final continueListeningProvider = FutureProvider<ContinueListening?>(...)
```

内部：从 `shelfProvider` 拿书 → 筛 `lastPlayedAt != null` → 取最新一本 → 取该书章节 → 组装 `(book, chapter?, chapterCountKnown)`。返回 `null` 表示「从未播放过任何书」，界面据此不渲染卡片。

依赖 `shelfProvider` 而不是自己查 DAO：书架同步完成后 `shelfProvider` 会失效重取，卡片跟着自动更新，不需要额外的失效链路。播放开始后书上的 `last_played_at` 会变，因此续播动作结束时一并 `invalidate(shelfProvider)`。

章节数组越界（`currentChapterIndex >= chapters.length`，刷新章节后变少）时 `chapter` 为 `null`，与「章节还没解析」同样处理：卡片显示书名与准备中提示，播放按钮禁用。这一条与历史页 `_resume` 的校验是同一类问题，值得用同一种口径。

### 决策 3：冷启动不自动播放

用户的原话是「点击就可以开始」——入口在首屏，动作仍由用户发起。自动播放的实际后果是：插着耳机启动就出声、车载蓝牙一连上就抢音频焦点、以及在用户只是想加本书的时候消耗网盘流量（非会员账号带宽本就受限）。这条写进规格，避免以后被当成「顺手加个开关」补上。

### 决策 4：有播放会话时卡片让位给迷你播放条

（真机验证后修正的决策。原方案是「卡片一直在，点它时短路回播放页」。）

底部的迷你播放条本来就常驻在所有页面上，播放一开始就显示当前书与章节。卡片再留着，同一本书在一屏上出现两次；更糟的是卡片读的是 `current_position_ms`——5 秒节流之前的位置，和播放条的实时位置对不上，看起来像两个互相矛盾的进度。

卡片要解决的是「刚打开 App，还没有播放会话」那一刻的事，播放条一出现它的职责就结束了。判定用与迷你播放条同一个数据源（`nowPlayingProvider` 包住 `handler.mediaItem`），保证两者同进同退，不会出现都在或都不在的中间态。流的首帧到达前用 `mediaItem.valueOrNull` 同步兜底，免得卡片闪一下再消失。

**备选方案**：卡片保留但改成显示实时位置。否决——那就是第二个迷你播放条，重复的是控件本身，不是数据。

### 决策 4b：续播 MUST NOT 冲掉当前播放位置

书架条目上的续播键仍然可能指向播放器里已经装着的那本书。此时再走一遍 `openBook` 会重新 `setAudioSource`，把正在播的位置冲回书上记录的断点，听感上就是「点一下倒退几秒」。

判定方式：比对 `handler.mediaItem` 当前值的 `extras['bookId']` 与目标书 id（`_mediaItemFor` 已经在 extras 里放了 `bookId`）。相同则直接 push 播放页，不碰音源。这条判断留在共用的续播函数里，卡片虽然此时已经不显示了，逻辑仍由列表入口用着。

**备选方案**：在 handler 上加 `currentBookId` getter。否决——`mediaItem` 是既有的响应式来源，加字段等于多一处要维护的状态。

### 决策 4c：卡片放在书架列表下方，不放顶部

（真机试用后按使用者要求调整。原方案放顶部。）

「最显眼」和「最好按」不是一回事。这是个单手拿着、经常在通勤路上点的 App，屏幕上半部分需要换手或改握姿才够得到，而续听卡片是每次打开都要点的那一下——它该落在拇指自然扫过的区域，也就是列表下方、导航栏上方。

代价：书多到需要滚动时，卡片在首屏之外。当前书架规模（个位数本）不构成问题；真到了那一步，做法是把卡片从滚动列表里拿出来钉在导航栏上方，而不是挪回顶部。

顺带去掉了原来用来分隔卡片与列表的「书架」小标题——卡片在下方时不需要它，AppBar 标题已经说明了这是书架。

### 决策 5：续播入口抽成一处

现在的 `_continueListening` 是 `_BookTile` 的私有方法。卡片要用同一套逻辑（含决策 4 的短路、源缺失与章节缺失的提示），因此抽到 `shelf_screen.dart` 的文件级函数或一个小的续播辅助里，两处调用。不抽的后果是两个入口对边界情况给出两种反应，而这正是用户最容易撞见的地方。

## Risks / Trade-offs

- **[卡片与列表首项重复]** 最近在听的书同时出现在卡片和下方列表里 → 接受。把它从列表里剔掉会让「书架有几本书」变得可疑，也会在卡片因源缺失而禁用时让这本书无处可点。视觉上靠卡片的不同形态与分隔标题区分。（与迷你播放条的重复不在此列——那是同一个控件职责重复，已按决策 4 让位。）
- **[章节查询让首屏多一步异步]** 卡片要等 `chapters(bookId)` 回来才完整 → 两次查询都是本地 SQLite，量级微秒；且卡片在书名可用时即可先渲染骨架，章节名后到。若实测有闪烁，退化为「先渲染书名 + 位置，章节名 late-bind」。
- **[`last_played_at` 由同步合并决定]** 多设备冲突解决取较大值（`library_snapshot.dart`），因此另一台设备上更晚的收听会成为首页卡片的内容 → 这正是期望行为（跨设备接上），但用户可能短暂困惑于「我在这台没听过这本」。卡片显示的是断点信息，不宣称设备归属，不额外处理。
- **[本次不做自动播放]** 部分用户可能就是想「打开即响」→ 明确记在 Non-Goals，等真实反馈再议；届时是一个设置项，而不是默认行为。
